# Аудит проекта passrw-bot

Дата проверки: 2026-11-04  
Коммит: `c3f5eab` (ветка `main`)  
Проверял: клонирование, статический анализ (pyflakes), установка зависимостей, живой запрос к pass.rw.by, тесты БД, Flask test client, симуляция многопоточного трекинга.

---

## 1. Краткий вердикт

Парсер pass.rw.by **работает на актуальной вёрстке** (проверен живой запрос: Минск → Москва, 2026-11-20, найдено 9 поездов с местами и ценами). Базовая логика поиска, календаря, карточки поезда, кнопки покупки и SQLite-хранилища в целом рабочая.

Но **проект нельзя запустить «из коробки»**, а несколько заявленных в README функций фактически не работают:

- установка по `requirements.txt` падает;
- первый запуск падает без вручную созданной папки `data/`;
- мультитрекинг (до 5 поездов) не работает корректно;
- остановка трекинга и успешное завершение не удаляют запись из БД — после перезапуска «остановленный» трекинг оживает;
- избранное и повтор поиска из истории сломаны;
- в веб-админке не работает переключение heartbeat, недоступна страница управления пользователями, `/api/statistics` отдаёт 500;
- в публичном репозитории лежит `.env` с паролем администратора `***REMOVED***` и рабочим `SECRET_KEY`.

## 3. Критические проблемы (P0)

### 3.1. Проект не устанавливается по инструкции

```
telebot-calendar>=1.3.0
```

На PyPI существуют только версии **1.1 и 1.2**, поэтому `pip install -r requirements.txt` завершается ошибкой и не ставит вообще ничего. README при этом обещает установку одной командой.

**Исправление:** зафиксировать `telebot-calendar==1.2` (и проверить совместимость API) либо перейти на поддерживаемую библиотеку календаря. Заодно закрепить остальные версии.

### 3.2. Первый запуск падает без папки `data/`

`tracking_sync.py` в конце модуля вызывает `create_sync_table()` (строка 440), который сразу открывает `data/ticket_bot.db`. `ticket_bot.py` импортирует `tracking_sync` (строка 23) **до** того, как `init_database()` создаст каталог `data/`. Итог на чистом клоне:

```
sqlite3.OperationalError: unable to open database file
```

То же самое у `admin_panel.py` (импорт `tracking_sync` в строке 51). В репозитории каталога `data/` нет.

**Исправление:** создавать каталог БД в `tracking_sync`/общем конфиге до первого `sqlite3.connect`, либо убрать побочный эффект из импорта модуля.

### 3.3. Секреты в публичном репозитории

Файл `.env` закоммичен (и присутствует в истории, коммиты `1aa5439`, `b9e6007`, `ae2a2ed`). В нём:

- `ADMIN_USERNAME=admin`, `ADMIN_PASSWORD=***REMOVED***` — **пароль совпадает со значением по умолчанию**;
- `SECRET_KEY` — не дефолтная строка, то есть это реальный ключ подписи сессий;
- `TELEGRAM_TOKEN` по формату похож на заглушку, но проверить и отозвать его всё равно нужно;
- `__pycache__/*.pyc` тоже закоммичены.

Если проект где-то развёрнут с этим `.env`, вход в админку `admin/***REMOVED***` доступен любому, а зная `SECRET_KEY`, можно подделать сессию.

**Исправление:** отозвать токен и сменить пароль/ключ, удалить `.env` из индекса (`git rm --cached .env`), вычистить историю (`git filter-repo`), включить secret scanning. `.gitignore` уже содержит `.env`, но файл был добавлен раньше.

### 3.4. Схема БД в `tracking_sync.py` не совпадает со схемой бота

Код синхронизации обращается к колонкам и таблицам, которых нет в `init_database()`:

| Что запрашивается | Где | Есть ли в схеме |
|---|---|---|
| `active_trackings.last_request_count`, `unique_token` | `tracking_sync.py:112,120,196,204` | нет |
| `active_trackings.is_stopped`, `updated_at` | `tracking_sync.py:143` | нет |
| `sync_flags.tracking_id`, `admin_username` | `tracking_sync.py:149-150` | нет |
| `sync_flags.admin` | `tracking_sync.py:369,377` | нет |
| таблица `request_counter_history` | `tracking_sync.py:228` | нет (нигде не создаётся) |

Проверено на практике:

```
request_tracking_stop(...) -> False   (no such column: last_request_count)
confirm_tracking_stopped(...) -> False (no such column: last_request_count)
```

Последствия:

- «мягкая» остановка из админки всегда падает и откатывается к принудительному удалению;
- любой штатный выход потока (`/stop`, удаление из админки) не может подтвердиться и **не удаляет запись из БД**;
- статистика запросов в `request_counter_history` не пишется.

**Исправление:** единая схема + миграции (например, `PRAGMA user_version` и набор миграций), один модуль доступа к БД для бота и админки, тест на согласованность схемы.

### 3.5. Успешный трекинг и остановка не удаляют запись (неверный аргумент)

Сигнатура:

```python
def remove_tracking_from_db(chat_id, tracking_id=None, train_time=None)
```

А вызовы:

```python
remove_tracking_from_db(chat_id, selected_time)   # ticket_bot.py:1160 (успех)
remove_tracking_from_db(chat_id, train_time)      # ticket_bot.py:1723 (/stop)
```

Время отправления передаётся **в параметр `tracking_id`**, поэтому удаление идёт по условию `id = '06:06'` и не удаляет ничего. Проверено: после вызова запись остаётся.

Последствия: после перезапуска `restore_active_trackings()` снова поднимает «остановленный» трекинг и продолжает слать уведомления; лимит в 5 трекингов забивается мусором; успешный трекинг уведомит повторно после рестарта.

### 3.6. Мультитрекинг фактически не работает

Заявлено до 5 поездов, но всё in-memory состояние ключуется только по `chat_id`:

```python
active_jobs = {}       # ticket_bot.py:856
tracking_status = {}   # ticket_bot.py:865
active_jobs[chat_id] = {...}  # ticket_bot.py:2170 — перезаписывает предыдущий
```

Симуляция двух трекингов (06:06 и 07:07):

```
После запуска 2 трекингов: active_jobs entries = 1, status train = 07:07
Потоки после появления мест в 06:06: 06:06 -> остановлен, 07:07 -> остановлен
Сообщений: 2, записей в БД: 2
```

То есть:

- статус и job хранят только последний трекинг;
- успех одного поезда делает `active_jobs.pop(chat_id)` и **останавливает потоки всех поездов пользователя**;
- записи в БД при этом остаются (см. п. 3.5), и после рестарта всё восстанавливается.

**Исправление:** ключ состояния — `tracking_id` (или составной `(chat_id, tracking_id)`), по одному потоку/задаче на трекинг, остановка строго по ID.

### 3.7. Переключение heartbeat в админке падает с 500

В `admin_panel.py` имя `toggle_heartbeat` определено дважды:

- строка 291 — функция работы с БД `toggle_heartbeat(tracking_id, enabled)`;
- строка 1838 — Flask-view `toggle_heartbeat(tracking_id)`, которая вызывает `toggle_heartbeat(tracking_id, new_status)`.

Вторая функция перекрывает первую, и view рекурсивно вызывает саму себя с двумя аргументами. Проверено: `POST /tracking/<id>/toggle_heartbeat` → **500**.

Даже если починить имя, изменение применяется только в БД; работающий поток читает интервал один раз при старте (`ticket_bot.py:1058`) и in-memory `heartbeat_enabled` не обновляет.

### 3.8. Дублирующийся маршрут `/users`

В `admin_panel.py` два обработчика на один URL: `users_list` (1880) и `users_management` (1983). Побеждает первый, поэтому страница управления пользователями (и ссылка на неё в сайдбаре) фактически недоступна. В шаблоне пользователей при этом всё равно нет формы смены роли — маршрут `/user/<id>/set_role` существует, но UI для него отсутствует.

### 3.9. `/api/statistics` всегда 500

`get_statistics()` возвращает `sqlite3.Row` в полях `popular_stations`, `top_users`, `top_routes`, `top_actions`, `top_error_types`, `recent_errors_preview`, `users_with_most_errors`. `jsonify()` их не сериализует:

```
TypeError: Object of type Row is not JSON serializable
```

Проверено: `GET /api/statistics` → 500. Дашборд (`/`) при этом работает, так как Jinja умеет читать Row.

### 3.10. Избранное и повтор поиска сломаны

1. В `telebot_calendar==1.2` нет метода `get_calendar()`; есть `create_calendar()`. А код вызывает `calendar.get_calendar()` в `on_repeat_search` (2300) и `on_favorite_search` (2367) → `AttributeError`.
2. Оба обработчика не выставляют `user_steps[chat_id] = 'ask_date'`, поэтому даже при наличии календаря `on_calendar_selection` ответит «Сейчас не требуется выбор даты».
3. В интерфейсе нигде нет кнопки, генерирующей `fav_add_...`, — добавить маршрут в избранное из результатов поиска невозможно. Обработчик `on_add_to_favorites` есть, но недостижим.
4. При удалении избранного вызывается **несуществующая** `show_favorites()` (`ticket_bot.py:2386`; pyflakes: `undefined name 'show_favorites'`). Удаление из БД проходит, но список не обновляется, а пользователь видит «Ошибка при удалении».

### 3.11. `/track` без предварительного `/start` ломает создание трекинга

Пользователь создаётся в БД только в `send_welcome()` (`/start`, строка 1268). Если сразу отправить `/track` (а README это разрешает), то при старте мониторинга `save_tracking_to_db()` и `save_search_history()` падают:

```
sqlite3.IntegrityError: FOREIGN KEY constraint failed
```

Обработчик callback не ловит исключение, поэтому пользователь не получает ответа. Проверено на чистой БД.

**Исправление:** `upsert` пользователя в `start_track` (и в любом обработчике входа), либо снять/ослабить FK и хранить пользователя отдельно.

### 3.12. Кнопки меню перехватываются как ввод станции

Общий обработчик шага (`ticket_bot.py:1861`) зарегистрирован раньше обработчиков reply-кнопок («📊 Мои трекинги», «🔙 Назад» и т.п., строки 2411+). Пока пользователь в процессе `/track`, нажатие «🔙 Назад» записывается как название станции. Нужен либо отдельный `cancel`-хендлер, зарегистрированный раньше, либо проверка текста на команды/кнопки внутри шага.

### 3.13. Ошибка при клике по пустой ячейке календаря

`calendar_query_handler` для действия `IGNORE` возвращает кортеж `(False, None)`. Код проверяет `if result:` — кортеж истинный, далее вызывается `result.strftime(...)` → исключение и alert «Ошибка при выборе даты» на каждый клик по заголовку/пустой ячейке. Проверено по исходнику библиотеки.

### 3.14. `callback_data` длиннее 64 байт для кириллических маршрутов

В `/history` данные кнопки собираются как:

```
repeat_search_Санкт-Петербург_Москва_2026-11-20_2
```

Обрезка проверяет **символы**, а Telegram ограничивает **байты**:

| Маршрут | Символов | Байт |
|---|---|---|
| Минск → Москва | 39 | 50 |
| Санкт-Петербург → Москва | 49 | 69 |
| Санкт-Петербург → Нижний Новгород | 58 | 86 |

Для длинных маршрутов Telegram отклонит отправку сообщения (`BUTTON_DATA_INVALID`), и `/history` перестанет работать. Нужно хранить в callback только ID записи истории и брать данные из БД.

## 4. Прочие функциональные и эксплуатационные проблемы (P1)

- **Пустой тип вагона.** В живом ответе встречаются элементы с `type: ''` (не «Неизвестный»), потому что fallback срабатывает только при отсутствии `div`, а не при пустом тексте. В карточке поезда будет «🛏 : 146 мест».
- **Валидация даты.** Регулярка `\d{4}-\d{2}-\d{2}` не заякорена (`re.match` пропускает `2026-11-20abc`), прошедшие даты при ручном вводе не проверяются (календарь проверяет, текст — нет).
- **Нет ограничения сверху на пассажиров** и нет проверки существования станции — ошибки всплывают только пустым списком поездов.
- **Heartbeat привязан к `chat_id`, а не к трекингу**: второй трекинг перезаписывает интервал первого; успех одного очищает heartbeat всех.
- **Feature flags и webhook — мёртвый код.** `is_feature_enabled()` нигде не вызывается; `webhook_events` только наполняется, отправки нет. A/B-тесты не работают.
- **Статистика пользователя неполная.** `successful_bookings` и `total_savings` никогда не увеличиваются; «конверсия» всегда 0.
- **Админские изменения heartbeat не доходят до бота** (только БД, см. 3.7).
- **UTC в `created_at`** отображается как локальное время (в `/mytracks` вывод даже закомментирован с пометкой «Отображает время в UTC»).
- **Один HTTP-запрос на каждый клик** «предпросмотр» и полный парсинг всей страницы на каждый цикл; нет кеша, ретраев, backoff и джиттера. При 5 трекингах на пользователя и нескольких пользователях это заметная нагрузка на pass.rw.by и риск блокировки.
- **`Accept-Encoding: br`** добавляется вручную, хотя `brotli` не в зависимостях; при ответе Brotli возможны проблемы с декодированием.
- **`fake_useragent`** инициализируется на каждый запрос (`ua.random`), при сбое пишет шум в лог; лучше статический пул UA.
- **Нет уникальности трекинга**: повторное нажатие «Запустить мониторинг» создаёт дубликат строки; ограничение «5» считает строки, а не уникальные поезда.
- **Ограничение 5 трекингов обходится** повторными callback-нажатиями до проверки, а потоков на пользователя всё равно больше одного не учитывается.
- **`requests_count` при рестарте** восстанавливается, но при успехе не сохраняется из-за п. 3.4/3.5.
- **Логи и история растут без очистки** (`user_logs`, `search_history`, `webhook_events`).
- **`admin_logs` создаётся внутри `log_admin_action()` на каждый вызов** — лишние DDL-запросы; лучше один раз при старте.
- **Нет тестов и CI.** Ни одного `test_*.py`; регрессии вроде 3.5–3.10 не отлавливаются.
- **Нет `LICENSE`** при заявленной MIT; в README остались артефакты (`cd /workspace`, «created with AI»).
- **Docker-инструкция копирует `.env` в образ** — плохая практика.
- **CSV-экспорт** не защищён от formula injection (значения, начинающиеся с `=`, `+`, `-`, `@`).

## 5. Безопасность админ-панели

- **CSRF-защиты нет**, хотя в docstring и README она заявлена: ни одного токена, ни `CSRFProtect`. `SameSite=Lax` частично смягчает, но не заменяет CSRF-токены.
- **Пароль хранится в открытом виде** в `.env`, `werkzeug.security` импортирован, но не используется. Нет хеширования/`check_password_hash`.
- **Нет rate limiting на `/login`** — возможен перебор; `RateLimiter` применён только к трём API-эндпоинтам.
- **`IP_WHITELIST`, `ENABLE_2FA`, `SESSION_TIMEOUT_MINUTES`** объявлены, декораторы `ip_whitelist_check` и `session_timeout_check` написаны, но **нигде не применены**. 2FA не реализована вовсе.
- **`SESSION_COOKIE_SECURE` не включён**; при доступе по HTTP (не localhost) cookie уходит открытым текстом.
- **Дефолтные секреты**: `ADMIN_PASSWORD="***REMOVED***"`, `SECRET_KEY="change-this-in-production"` — если `.env` отсутствует, приложение стартует с предсказуемыми значениями.
- **Flask dev-server** (`app.run`) в production не предназначен; нужен gunicorn/waitress + reverse proxy с HTTPS.
- **Токен частично печатается в лог** (`***` + последние 5 символов) — мелочь, но лучше не логировать.
- `.env` в публичном репозитории — см. п. 3.3.

## 7. Предложения по улучшению функциональности

1. **Починить установку и старт**: `telebot-calendar==1.2`, создание `data/` до первого подключения, `python -m venv` + lock-файл, проверка `python ticket_bot.py` в CI.
2. **Ввести миграции БД** (`user_version` + SQL-миграции) и один общий модуль `db.py`; синхронизировать схему `active_trackings`, `sync_flags`, `request_counter_history`.
3. **Ключевать трекинг по `tracking_id`** во всех in-memory структурах, потоках, status и heartbeat. Добавить `UNIQUE(chat_id, from_station, to_station, date, train_time)` и идемпотентный старт.
4. **Исправить удаление**: всегда `remove_tracking_from_db(chat_id, tracking_id=...)`; на успехе и остановке вызывать `confirm_tracking_stopped` и удалять ровно один трекинг.
5. **Починить админку**: убрать дубль `/users`, переименовать DB-функцию heartbeat, сериализовать Row в `/api/statistics`, применить `session_timeout_check`/`ip_whitelist_check`/CSRF, хешировать пароль.

7. **Upsert пользователя** при `/track` и в callback-обработчиках.
8. **Отдельный `/cancel`** и приоритет команд/кнопок над обработчиком шага.
9. **Написать pytest-тесты** на: парсер (фикстура HTML), удаление/остановку, мультитрекинг, схему БД, админские роуты. Добавить ruff/pyflakes в CI.

### Повышение надёжности (P1)

10. **HTTP-клиент**: одна `requests.Session`, фиксированный пул User-Agent, retry с экспоненциальным backoff и jitter, таймауты, кеш ответа на 30–60 секунд на маршрут, убрать `br` из `Accept-Encoding`, уважать rate limit сайта.
11. **Сопоставление поезда по номеру + времени**, а не только по времени: сейчас два поезда с одинаковым временем отправления неразличимы, а сдвиг времени в расписании навсегда ломает трекинг.
12. **Уведомления без спама**: одно уведомление при появлении мест, затем только при росте количества/изменении цены; настраиваемый порог («уведомить, если ≥ N мест»).
13. **Планировщик вместо потока на каждого пользователя**: APScheduler/очередь с ограничением параллелизма и джиттером; это же решит проблему «5 трекингов × N пользователей».
14. **Валидация станций** через autocomplete/API pass.rw.by (или справочник станций), проверка даты (не в прошлом, корректный календарный день), максимум пассажиров.
15. **Ретеншн данных**: очистка `user_logs`/`search_history`/`webhook_events` старше N дней, индексы под частые выборки.
16. **Консистентное время**: хранить UTC и конвертировать в часовой пояс пользователя/Минска при выводе.

### Новые возможности (P2)

17. **Автодополнение станций и валидация маршрута** до запроса — меньше пустых поисков и запросов к сайту.
18. **История наличия мест и цен**: график «мест по времени», тренд цены, уведомление о снижении цены. Данные уже можно копить в отдельной таблице.
19. **Гибкие фильтры**: тип вагона (плацкарт/купе/СВ/сидячий), диапазон цены, нижние места, конкретный вагон.
20. **«Тихие часы» и расписание уведомлений** (не будить ночью), выбор языка уведомлений.
21. **Шаринг маршрута** ссылкой/кнопкой «поделиться трекингом», совместное отслеживание для компании.
22. **Настройки профиля**: пассажиры по умолчанию, любимые станции, интервал проверки, автостоп после покупки.
23. **Админка**: healthcheck `/healthz`, метрики (Prometheus), графики нагрузки на парсер, управление блокировками пользователей, массовые рассылки с подтверждением, аудит действий (уже есть основа).
24. **Деплой**: Dockerfile + docker-compose (bot + admin + volume для `data/`), gunicorn/waitress для админки, reverse proxy с HTTPS, systemd-юниты, `.env` только через secrets.
25. **Наблюдаемость**: Sentry/структурированные JSON-логи, алерты при серии ошибок парсинга и при «трекинг не находит поезд N циклов».

## 9. Итог

Проект — хороший прототип с рабочей идеей и живым парсером, но в изначальном состоянии это **демо, а не готовый к эксплуатации сервис**. Наиболее опасны: секреты в публичном репозитории, неработающая остановка/удаление трекингов, сломанный мультитрекинг и рассинхронизация схемы БД. После исправления P0 проект можно уверенно запускать в ограниченном кругу, а после P1 — развивать функционально.
